
## EmotionTokenTextView 插入光标高度修正（2026-10-20）
- bug：`bodyLineSpacing = 28` 把行片段撑到 ≈44.5pt，NSTextView 默认按整个行片段画蓝色插入 caret，光标比字形高一截、下探到两行空隙。
- 修复：override `drawInsertionPoint(in:color:turnedOn:)` 自绘 caret——高度只取字体自然高度（ascender-descender），在该行 `lineFragmentUsedRect`（不含行距空白）内垂直居中；末尾换行的空行走 `extraLineFragmentUsedRect`；拿不到布局时贴行顶；最后夹回系统给的插入点矩形兜底。熄灭相交给 super 擦除（擦整个行片段，必覆盖小 caret，闪烁不受影响）。
- 验证：`swiftc -typecheck` 全 target 通过（exit 0，仅既有无关警告）。
- 追加（同日二修）：caret 垂直位置偏低、下沿超出胶囊——原因是用了 `lineFragmentUsedRect` 居中，它跟字形度量不同口径。
  改为与胶囊同源的基线算法 `baseline = lineRect.minY + location(forGlyphAt:).y`，caret = baseline-ascender .. baseline-descender，
  正好等于胶囊夹住的文本区。新增私有方法 `insertionPointTextTop(container:layoutManager:)`。
  ⚠️ 经验：本项目的垂直几何一律用「基线 ± 字体度量」，不要用 lineFragmentUsedRect / boundingRect 的高度。

## 积分体系改造方案（问题 2 + 问题 3）—— 只出方案，未改 Swift 源码

产出三份：
1. `supabase/migrations/20261020_credits_hardening.sql`（幂等迁移，待用户在 Dashboard 执行）
2. `docs/积分体系改造方案.md`（根因 / 目标架构 / 客户端逐文件改造点 / 分阶段落地 / 回滚 / 验证清单 / 待决策）
3. `supabase/functions/verify-purchase/index.ts`（内购服务端入账骨架，`deno check` 退出码 0）

### 方案核心
- **问题 2**：收回 anon 对 `user_credits` 的 INSERT/UPDATE（只剩 SELECT）；
  建 `credit_ledger` 流水账本，`(device_id, op_id)` 唯一 = 幂等硬保证；
  三个 SECURITY DEFINER RPC：`ensure_user` / `consume_credits`（anon 可调）/
  `grant_credits`（**仅 service_role**）。
  扣费用单条 `UPDATE ... WHERE credits >= amount RETURNING` 靠行锁防并发超扣。
- **问题 3**：云端为唯一权威，本地 = 云端快照 − Σ(pending 扣费) + Σ(未入账内购)；
  pending 账本落**独立 JSON 文件**；失败暴露 `syncState` 而非静默打日志；
  内购改走 `verify-purchase` 服务端入账，op_id = transactionId 幂等。

### 两个关键洞察（长期有效）
- **pending 账本绝不能放进项目 SQLite**：`DatabaseManager` 的策略是「结构版本不符就
  DROP 全部表重建」，某次 bump `currentFingerprintVersion` 会把用户还没上报的扣费记录
  清空 → 又变丢钱。改用 `~/Library/Application Support/<bundle id>/credits_pending.json`
  + 原子写，顺带避开 SQLite Connection 跨线程不安全问题。
- **客户端侧鉴权（APP_SECRET / HMAC）防不住专业攻击者**：secret 明文在二进制里，
  逆向即可伪造。方案能防住「随手 curl 改余额 / 并发超扣 / 重复扣费 / 负余额」，
  **防不住「冒用他人 device_id 花光别人余额」**（DoS）。根治只有 Supabase Auth
  匿名登录 + RLS 用 `auth.uid()`。别误以为迁移完就安全了。

### 落地顺序
阶段 0（建表 + RPC + 授权，**先跳过脚本第 3 节 revoke**）→ 观察 1~2 天 → 单独执行 revoke。
因为 revoke 后老客户端 `saveOrUpdateUser` 会直接 403、启动即报错，必须与新版本协同。
