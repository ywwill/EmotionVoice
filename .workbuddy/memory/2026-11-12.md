## macOS 阅读区：换行时播放底色不再熄灭
- 现象：`PlayerTranscriptView` 一行播完切下一行时，播放底色会「消失一下」再出现在下一行。
- 根因：`AudioTimeline.location(at:)` 在**句间停顿**里返回 `index = nil`（只有 previous/next），而底色 / 左侧竖条 / 时间码色全按 `isActive = cue.index == activeIndex` 画 → 停顿期间整页没有一行亮着（停顿越长灭得越久），下一句起播才重新亮。
- 改法（仅 macOS，`View/macOS/HistoryView/PlayerTranscriptView.swift`）：
  - 新增 `highlightIndex(atMs:location:)`：有当前句且有正文 → 就是它；否则（停顿 / 落在纯标签句上）交给**下一句有正文的句子**。底色、竖条、时间码、跟随滚动统一用它，不再用 `activeIndex`。
  - `visibleCues`（有正文句的 `index + beginMs`）在 `AlignedTranscript.init` 里算一次并 `let` 存住 —— ⚠️ 别改成 body 里现算（那是 10Hz 路径）；也别用 `location.next` 当交棒目标（`[clears throat]` 独占一句时界面上没有那一行，交过去等于没亮）。
  - `scrollCurrent(proxy, to:)` 简化为只吃 highlight；`.onChange(of: highlight ?? -1)` 触发 —— 滚动与高亮同一拍，全程永远一行亮着，整段播完（没下一句）才真的熄灭。
- 验证：`bash tools/ios_build.sh mac` 双 target BUILD SUCCEEDED；`/tmp/hl_check.swift` 10 条断言（普通停顿 / 中间夹纯标签句 / 结尾纯标签句 / 前导静音）全部符合预期。

## macOS 阅读区：换行时底色改成「滑动」补间（0.34s）
- 需求：一行播完切到下一行时，播放底色要「自然平滑地移动过去」，而不是灭一下/闪一下。
- 上一版的问题：底色是**每行各自一块**（`background(isActive ? accentWash : .clear)` + `.animation(0.18, value: isActive)`），两块视图之间只能「旧的淡出 + 新的淡入」——换行那一刻必然出现两个半透明块同时存在/交替，观感是闪。
- 改法（仅 macOS，`View/macOS/HistoryView/PlayerTranscriptView.swift`）：
  - 底色变成**整篇唯一一块**：`AlignedTranscript.highlightLayer(_:)` 画在内容 VStack 的 `.background(alignment: .topLeading)` 里，尺寸/位置由行 frame 决定。换行时只是这一块的 `offset`/`height` 变化 → SwiftUI 补间成一次连续位移（真·滑过去），左侧竖条同一块里一起走。
  - 行位置：每行 `.background { GeometryReader { $0.frame(in: .named(contentSpace)) } }` 上报 `TranscriptRowFrameKey`，落成 `@State rowFrames`。坐标系挂在**内容 VStack**（`(.coordinateSpace(name:)`）而不是视口 → 滚动不会改值，10Hz 播放路径里没有 preference 抖动。写入 state 前用 `sameFrames`（0.5pt 容差）挡掉亚像素抖动，避免「写 state→重排→再上报」自激。
  - `.animation(.easeInOut(duration: highlightTravel), value: highlight)` **只挂在底色这一层**；逐字高亮照旧不受影响。`scrollCurrent` 从 `.easeOut(0.22)` 改成 `.easeInOut(0.34)`，与底色同值同曲线 —— 两者同拍时视口正好把下一行送到上一行的位置，屏幕上底色几乎不动、只做高度过渡，不会出现「底色和文字互相追」。
  - 移除 `SentenceCueRow` 里的 `background` / `.animation(value: isActive)` / 竖条 `overlay`（`isActive` 仅剩时间码配色用途）。
- 验证：`bash tools/ios_build.sh mac` 双 target BUILD SUCCEEDED；另写 `/tmp/slide_demo.swift`（独立 SwiftUI 复现，动画放慢到 1.2s）连拍截图，确认中间帧的底板确实**横跨两行之间**（插值中），而不是两块独立淡入淡出。⚠️ 编译该复现脚本需 `swiftc -disable-sandbox -parse-as-library`（沙盒里 SwiftUI 宏插件起不来）。
- iOS `PlayerDetailControls.swift` 暂未改，用户仍要求先只做 macOS。

## iOS AVAudioSession Hang Risk（11-12 第五轮）
- 现象：Xcode 27.2 运行时诊断 `This method can lead to UI unresponsiveness if called on the main thread. Consider using the asynchronous activate/deactivate API instead...`，点名 `AudioPreviewPlayer+iOS.swift` 的 `p.prepareToPlay()`（166）与 `setActive(false)`（494）。根因：`setCategory`/`setActive` 是到 mediaserverd 的同步 XPC；`prepareToPlay()` 会 acquire 音频硬件，同样阻塞主线程。类整体 `@MainActor`，所以全在主线程。
- ⚠️ **不能用警告建议的异步 API**：SDK 头文件 `AVFAudio/Headers/AVAudioSession.h:278/287` 明确 `activateWithOptions:completionHandler:` / `deactivateWithOptions:completionHandler:` 是 **iOS 27.0+**，而工程 `IPHONEOS_DEPLOYMENT_TARGET = 17.6`。正解是把同步调用搬离主线程。
- 修（只改 `View/iOS/Services/AudioPreviewPlayer+iOS.swift`）：新增文件级串行队列 `audioWorkQueue` + `AudioSessionWork`（activate/deactivate/makePreparedPlayer）+ `PreparedPlayerBox: @unchecked Sendable`；`play(url:)` 把 session 配置、`AVAudioPlayer(contentsOf:)`、`prepareToPlay()` 全放队列，结果经 `Task { @MainActor }` 回主线程 `finishStartPlayback` 做 `delegate`/`play()`/状态发布（`AVAudioPlayerDelegate` 回调仍走主线程 RunLoop）；`activateSession()`/`deactivateSession()` 也只派发队列。
- ⚠️ 队列必须**串行**：`stop()` 的停用 → `play()` 的激活 → 创建/预热靠 FIFO 保序，不能换 concurrent queue 或 Swift actor（actor 不保证任务顺序）。
- ⚠️ 异步起播引入竞态：`playRequestSerial`（UInt64）在 `stop()` 与 `play(url:)` 各 `&+= 1`，回主线程只认最后一次；用户取消 / 快速切歌时旧的预热结果作废。
- ⚠️ 嵌套 `[weak self]` 会触发 `ImplicitStrongCapture`（默认 MainActor 下外层方法作用域是隐式强引用）；改用 `let owner = self` 强捕获 + `Task { @MainActor }`（单例不成环）。`var box/failure` 要先快照成 `let` 再交给并发闭包。
- ⚠️ 顺带修一个老 bug：`AVFAudio/Headers/AVAudioPlayer.h:81` 要求 `enableRate` 在 **`prepareToPlay()` 之前**设置，旧实现反着写（先 prepare 再 enableRate/rate），倍速实际失效；现在在队列里 `init → enableRate=true → rate=快照值 → prepare`。`play(url:)` 返回 Bool 语义变为「请求已受理」（调用方均忽略返回值），真正起播晚几十 ms。
- 保留：`play(url:)` 公开签名与 macOS 版一致；`configureMediaSessionIfNeeded()`（UIApplication / MPRemoteCommandCenter）仍主线程；`resume()`/中断恢复/锁屏重播的 `activateSession()` 保留幂等兜底。
- 验证：`typecheck.sh` exit 0 / 0 error / 10 条既有 warning（本文件 0 warning）；`ios_build.sh mac` 双端 **BUILD SUCCEEDED**、0 error。真机需确认：快速切歌不串音、锁屏续播、倍速 0.5x~2x 现在真的生效。

## Localizable.strings 五语言翻译（11-12 第六轮）
- 背景：用户已把 ru/ko/ja/fr/de 五个 `.lproj` 与 `knownRegions`、`PBXVariantGroup` children（Localizable + VoiceCatalog 两组）都挂进 pbxproj，但 `Localizable.strings` / `VoiceCatalog.strings` 全是 `en` 的原样副本（MD5 全等），App 里切语言仍显示英文。
- 需求口径：**中文 key 保持不变，以右边英文 value 作翻译源**；`.localized()` 是中文原文当 key，动 key 会全端失效。
- 新增可复现资产 `tools/localization/`：`build_localizable.py` 读 `en.lproj/Localizable.strings` 逐行替换 value（注释/空行原样保留），译文源在 `translations/{ru,ko,ja,fr,de}.txt`，每行一条、顺序与 en 的 537 条 key-value 严格对齐。`--check` 只校验不写。
- ⚠️ 译文源里**禁写裸 `"` 和反斜杠**，用 `<NL>`（→ `\n`）、`<Q>`（→ `\"`）标记，脚本 materialize 后写入；否则 JSON/`.strings` 二次转义必然踩坑。校验强约束：占位符 `%@/%d` 按**出现顺序**与英文完全一致（`String(format:)` 按顺序消费参数，调序会串值，尤其 `句间停顿 %@ · 下一句 %d`）、行数 = 537、无裸 `%`。
- 翻译口径：积分统一 Credits/баллы/크레딧/クレジット/crédits/Credits；引号按语言习惯（俄 «»、日「」、法 « »、德 „ “），不引入 ASCII 双引号；`ASMR`、`OK`、`Format`、`Dimension`、`Pause` 等与英文同形词属正常，非漏翻。
- 验证：5×537 条 0 error；`plutil -lint` 5/5 OK；key 集合与 en 完全一致（missing/extra 0）；`bash tools/ios_build.sh` **BUILD SUCCEEDED**（18s）；产物 `iOSEmora.app` 含 8 个 `.lproj`，5 个新语言的 `Localizable.strings` 均通过 lint。
- ⚠️ **遗留**：五个语言的 `VoiceCatalog.strings` 仍是英文副本（1202 行，由 `tools/gen_basic_voices.py` 生成、文件头写明勿手改）；音色名是专有名词通常不译，但 `.feature` 特质文案需要本地化，要改必须改生成器，别直接编辑 `.lproj`。

### 更正上条「遗留」：VoiceCatalog.strings 不需要翻译（同日核实）
- 上面那条判断有误，实际是**死文件、读不到**。`VoiceCatalog.lprojCandidates(for:)` 为 `guard language == .zh else { return ["en"] }`；`VoiceLangCode` 只有 `.zh/.en`；`VoiceService.rowToVoice` 只调 `.zh`/`.en` 各一次烘焙成 `name/nameEn`、`desc/descEn`；`Voice.localizedName/localizedDesc` 只看 `AppLanguage.isChinese`（`preferredLocalizations.first.hasPrefix("zh")`）二分，俄韩日法德界面一律走英文。所以 `ru/ko/ja/fr/de.lproj/VoiceCatalog.strings` 没有任何引用路径。

### 追问：音色名称要不要加其他语言版本（同日）
- 数据核查：599 个音色 `lang` 分布 = zh 591 / en 8，tier = premium 2 / basic 597；中文名平均 3.1 字；英文名 599 个全不重复、全 ASCII。样例「龙安灵心→Lynn」「璨竹月→Abigail」「蓉芷荷→Ada」＝**重新命名（transcreation）**，不是直译也不是拼音。
- 繁体版：369/599 与简体文本不同，但字数不等 0 条，全是纯字形 s2t（龙→龍、灵→靈、风→風），无用词差异 → 繁体是同一套中文名的字形变体，不构成「第三种语言版本」，不能拿它论证该按语言扩展。
- 落盘耦合：`DraftSnapshot.voiceName` / `Draft` 的 `case voiceName`、`ConsumptionRecord.voiceName` 存的都是**名字文本**（对比 `Draft.autoTitleKey` 只存中文 key、显示时 localized，项目已专门规避过文本落盘串语言的坑）；`VoiceService` 的 `sortName`（:154）与 `matchesSearch`（:336）都吃 `localizedName`。按界面语言切名字 ⇒ 草稿/账单名字定格在保存时语言、排序与搜索结果随语言漂移。
- 结论：**不加，继续用英文版**（现状即如此，且代码 `lprojCandidates` 已把 en 定为所有非中文界面的统一 fallback）。若某市场要做本地化运营，只给少量主推音色起当地名（品牌命名，非翻译任务），并先把落盘 `voiceName` 改成存 key。
