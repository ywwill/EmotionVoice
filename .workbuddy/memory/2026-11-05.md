## 复盘：删除 `skipStep` / `longSkipStep` 两个私有常量

用户质疑「声明两个属性有什么意义」。评审结论：**意义不大，已删**，4 处改回 `player.skip(by: ±15/±5)` 字面量，与 macOS `PlayerTransportView` 写法一致。
理由：
1. 每个常量只被引用 2 次，且都是 ± 成对，没有「多处复用」的收益；
2. 数字语义已由 SF Symbol 名 `gobackward.15` / `gobackward.5` 表达，抽常量后变成两处各自维护，改图标忘了改常量就会静默错位；
3. 用户明确要求参考 macOS，而 macOS 就是字面量；
4. 更关键的是「半吊子抽象」：真正重复出现 15 的地方是 `AudioPreviewPlayer+iOS.swift` 的锁屏远程命令（`preferredIntervals=[15]` ×2、`engine.skip(by: ±15)` ×2），View 私有常量管不到，容易误导后来人以为改这里就能全局生效。

什么时候才值得抽：只有把步长上移到 `AudioPreviewPlayer` 层、`View` 与远程命令共用同一个 `static let remoteSkipSeconds` 时才有价值；那种情况下应同时改图标（或由数据驱动生成按钮），否则别抽。

## macOS 启动窗口：消除「先小窗、再全屏」的跳变

需求：macOS 打开时窗口先是小窗，随后才铺满屏幕。

改动（只动 `View/macOS/EmotionVoiceApp.swift`）：
- Scene 加 `.defaultSize(width:height:)`，用 `NSScreen.main.visibleFrame` 动态算，窗口出生即最终尺寸。
- 新增 `LaunchWindowSizing`：统一可视区域 / 最小尺寸 / 极小屏退化规则，Scene 与 WindowAccessor 共用，避免两处逻辑分叉导致二次调 frame。
- `WindowAccessor` 改为自定义 NSView 子类，在 `viewDidMoveToWindow()` **同步**配置（透明标题栏、背景色、minSize、frame 校正），去掉 async；frame 已相同就跳过，`setFrame(_, display:false)` 不强制同步重绘。
- `AppDelegate.init()` 清掉所有 `"NSWindow Frame "` 前缀的 UserDefaults 键；配置时 `setFrameAutosaveName("")`，保持「每次启动铺满可视区域」的语义。
- `LaunchWindowCoordinator` 兜底：万一窗口先上屏，先 `alphaValue=0`，配置完成后 0.12s 淡入；带 0.8s 超时恢复与启动 0.5s 时间窗，避免误闪或窗口一直透明。
  - ⚠️ AppKit **没有** `NSWindow.didBecomeVisibleNotification`（编译报 `type 'NSWindow' has no member`），改用 `NSWindow.didBecomeMainNotification` + `didBecomeKeyNotification`，selector 版同步接收。

验证（`swift` 脚本用 `CGWindowListCopyWindowInfo` 每 8ms 采样窗口 bounds，不需要辅助功能权限）：

- `xcodebuild -project … -scheme Emora -sdk macosx …` → **BUILD SUCCEEDED**（最终代码重新构建过一次）；测试实例已 kill，Xcode 临时开关按原值还原。

## AudioPreviewPlayer(macOS)：12 条 captured var 'self' 并发告警

`Shared/Services/AudioPreviewPlayer.swift` 报 12 条 `Reference to captured var 'self' in concurrently-executing code; this is an error in the Swift 6 language mode`（首条 253:21）。

根因：`[weak self]` 在 `@Sendable` 并发闭包里是可变的 weak var 捕获，`Task { @MainActor in self?.xxx }` 引用了它；Swift 5 模式只 warning，Swift 6 是 error。12 处分布：KVO `AVPlayerItem.status` 观察 6 处（253/254/255/257/261/262）、`AVPlayerItemDidPlayToEndTime` 通知 5 处（278–282）、10Hz 进度 Timer 1 处（435），正好对应文件里全部 `self?.`。

- 不用改：`AVAudioPlayerDelegate` 两个 `nonisolated` 方法（现 522/536 行）的 `Task { @MainActor in self.xxx }`，那里 self 是隐式 let 参数，不触发本警告。

- 若将来真切 Swift 6 严格模式，还需另外处理 KVO/Task 中对 `AVPlayerItem`、`AVPlayer` 这类非 Sendable 对象的捕获，以及 nonisolated delegate 的 actor 跳转。

## VoiceStudioViewModel：#ImplicitStrongCapture（423:59）

`Shared/ViewModels/VoiceStudioViewModel.swift:423:59`：`'weak' ownership of capture 'self' differs from implicitly-captured strong reference in outer scope`。408 行外层 `Task {}` 隐式强捕获 self（443/484/496/… 都在用 self），423 行 `onAudio` 却写 `[weak self]`，所有权表达冲突。

⚠️ **纠正上面 AudioDuration 段落里的判断**：「若要真正修生命周期则外层也得 weak 化」是**错误方向**。生成结束要写回 `isGenerating` / `generatedAudioURL` / `stats`，且 533 行注释明确「弹窗可能早就被关掉了，靠 `generationCompletedSignal` 由全局浮层重新唤起」——设计上就要求 Task 期间 VM 存活。外层 weak 化会让关掉工作台后生成结果无处可写。同样，`onAudio` 在 `BailianTTSService` 里只作局部参数沿 `synthesizeStream → synthesizeAsync → performSynthesize` 传递，在 while 循环里 `onAudio?(binaryData)`（242 行），**不存为属性**，所以内层 `[weak self]` 不是防长期泄漏，而是让取消后残留的 WebSocket 回调安全失效，必须保留。

编译器 note（日志 265–266、274 行）给两个静音方式：
- 外层 `Task { [self] in ... }` — `add 'self' as a capture list item to silence`
- 内层写显式赋值 `{ [weak self = self] audioChunk in ... }` — `explicitly assign the capture list item to silence`

采用前者：408 行 `Task {` → `Task { [self] in`，并在上方加 3 行注释写明「外层强持有是有意设计 / 内层 weak 是取消后的安全失效」。只是把已有的隐式强捕获显式化，**零行为变化**；内层 `[weak self]` + `guard let self` 原样保留。

验证（**必须做基线对照**）：⚠️ 增量构建不重编该文件时日志里根本没有这条诊断，只 grep 会误判「本来就没警告」。先 `touch` 该文件再 `bash tools/ios_build.sh mac`，基线在 iOS arm64 / x86_64 + macOS arm64 **三个架构各复现一条** 423:59；改后再构建，三架构均真实重编、诊断归零，全文 `warning:` 只剩两条无关的 AppIntents 元数据提示，双 target `BUILD SUCCEEDED`。该文件里用户已有的 `await AudioDuration.read`（481 行）完整保留。

## GenerationDialog:533 —— 默认 MainActor 隔离（本轮所有隔离诊断的总根因）

用户报 `View/iOS/Views/Generation/GenerationDialog.swift:533:36 main actor-isolated static method 'envelope(url:barCount:)' cannot be called from outside of the actor`。基线无需重跑：上一轮 `/tmp/ev_fix_two.log` 304/359 行已复现；`git show HEAD` 确认 HEAD 版就是 `Task.detached { AudioWaveformExtractor.envelope(...) }`。

⚠️ **第一次尝试失败**：只给 `AudioWaveformExtractor.cache` 加 `nonisolated(unsafe)`（当时误判为「非 Sendable 静态属性被推断为 @MainActor，连带 envelope 被推断」），构建后 533:36 依旧。说明根因不在属性推断。

真根因：pbxproj 四个配置都设了 `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` + `SWIFT_APPROACHABLE_CONCURRENCY = YES`，`SWIFT_VERSION = 5.0` —— **整个 target 的声明默认 @MainActor 隔离**。这同时解释了前面 `EmotionTokenStyle.default` 为何被判 MainActor（结构体含 NSFont/NSColor 只是表象之一），以及 `#ImplicitStrongCapture` 那类隔离冲突。

修法（`View/iOS/Services/AudioFileSupport.swift`，仅此一文件）：`AudioWaveformExtractor` 是纯计算工具，给**三个方法全部**加 `nonisolated`（`envelope` / `cacheKey` / `extract`）—— 只改 `envelope` 会因同步调用另两个默认隔离的私有方法而报错；`cache` 保留 `nonisolated(unsafe)`（NSCache 线程安全但非 Sendable）。**没改调用方**：`Task.detached` 原样保留，解码仍在后台线程（`loadWaveform()` 注释明确「解码在后台线程，只把包络写回主线程」），改成 `MainActor.run` 会把 AVAudioFile 解码搬回主线程，是错误方向。

验证：`touch` 调用方 + `bash tools/ios_build.sh mac` → `AudioFileSupport.swift` / `GenerationDialog.swift` 在 iOS arm64 + x86_64 均真实重编，533:36 归零，全文 `warning:` 只剩 1 条无关的 AppIntents 元数据提示，双 target `BUILD SUCCEEDED` + `✅ 全部构建通过`。

教训：在默认 MainActor 隔离的工程里，「让一个方法能在后台跑」要顺着**整条同步调用链**一起 `nonisolated`，漏掉私有 helper 就会连锁报错；排查隔离问题先看 pbxproj 的 `SWIFT_DEFAULT_ACTOR_ISOLATION`，别只盯着单个声明猜推断规则。
