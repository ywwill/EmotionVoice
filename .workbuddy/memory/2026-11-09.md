## iOS 输入框：空行出现空白圆角背景框（已修）

现象：创作页正文里凡是「只有换行、没有文字」的空行，都会出现一枚十几 pt 宽的
灰白圆角小框（截图 2026-11-09 09.09）。

**根因**：`View/iOS/Views/Studio/TokenCapsuleOverlay.swift` 的 `lineRects()` 用
`enumerateLineFragments` 把语气标签作用域按行切段。换行符在 TextKit 里同样占一个行片段，
但它的 `boundingRect` 宽度是 0；旧逻辑 `r.size.width = max(hi - r.minX, 1)` 把它兜成 1pt，
再在 `draw()` 里 `insetBy(dx: -capsulePadX = -6, dy: -6)` 外扩 → 空行里凭空画出一枚
约 13×31pt 的胶囊。不是标记数据坏了，是绘制层把「无字形的行」当成了正文。

**修复（只改这一个函数）**：枚举每个行片段时，先用
`lm.characterRange(forGlyphRange:actualGlyphRange:)` 取出对应文档串片段，
`CharacterSet.whitespacesAndNewlines` 全命中就 `return` 跳过；`length == 0`（换行/控制字形
拿不到字符映射）同样跳过。⚠️ U+FFFC 占位符**不算空白**，含它的片段必须保留（拟声 pill /
语气留白有实际宽度）。过滤后 `pieces.isEmpty` 时原有「只画徽章不铺胶囊」分支自动接管。
⚠️ 别改 `lineRects` 里已有的 1pt 宽度兜底：它还要救「拿到 0 宽的真实文字行」。
⚠️ 局部变量名别用 `hi`（同函数下方已有 `let hi = min(r.maxX, usedRect.maxX)`，会 redeclare）。

**验证**：`tools/ios_typecheck/typecheck.sh` 0 error（仅 2 条既有 warning，无新增并发违规）；
Foundation 冒烟：`"\n"`/`"\n\n"`/`" \t\u{3000}\r\n"` → 判空 true，
`"文字\n"`/`"\u{FFFC}"` → false。
`tools/ios_build.sh` 最终 **BUILD SUCCEEDED**（49s）。前 3 次被环境阻断在
Resolve Package Graph：`swift-asn1` 的 SPM 缓存缺 tree 对象 `917b472d…`
（`fatal: unable to read tree`），与代码无关。修复方式（非破坏性、别删缓存目录）：
```
G="$HOME/Library/Caches/org.swift.swiftpm/repositories/swift-asn1-7065ad2c"
B=/tmp/iOSBuildDD/SourcePackages/repositories/swift-asn1-7065ad2c
git -C "$G" fetch origin 917b472dbe53ba699cbb0495f9a95a084bc6364d
git -C "$B" fetch "$G" 917b472dbe53ba699cbb0495f9a95a084bc6364d
```

## macOS 输入框：语气标签背景框在空行处重叠（已修，与上条同源）

现象（截图 09.04 + 用户补充「那一行没有文字、只是换行时就会出现」）：正文每段带金色

与 iOS 上条的差别：iOS 是空行凭空多一枚小白框，mac 是空行胶囊**被推到下一行**造成重叠。

**根因**：`EmotionTokenTextView.toneCapsuleGeometries()` 按 `enumerateLineFragments`

独立 AppKit 探针（`/tmp/ev_linefrag_probe.swift`，`lineSpacing=28`）实测：
正文行 `loc.y = 14`，**纯 `\n` 行 `loc.y = 45`（行底）**，`boundingRect` 宽度还是整行 400。
于是空行胶囊 top 比正确位置低一整行，正好压在下一行正文胶囊上。
探针 `/tmp/ev_capsule_probe.swift`：含 2 处空行 → 6 块胶囊、2 组重叠（各 14.49pt）；
过滤空行 → 3 块、0 组重叠。

**修复**（`EmotionTokenTextView.swift` + `EmotionToken/README.md`）：
- 新增 `capsuleInvisibleCharacters`（whitespacesAndNewlines + U+3000 + U+FFFC）。
  macOS 的 `scope.segments` 已把拟声标记字符切出，所以「纯附件行」也判空；
  ⚠️ **iOS 端相反**：U+FFFC 必须保留（占位符有实际宽度），别把两端判空集合互相抄。
- `toneCapsuleGeometries()` 加 `textStorage` guard；回调里用
  `characterRange(forGlyphRange:)` 取该行文本，trim 后为空就 `return`，
  **rects / textRects / lineKeys 三者必须一起跳过**（索引要对齐）。
- 空作用域仍走 `markerAnchor` 兜底最小胶囊，徽章不丢；绘制与命中同源
  （`tokenHitRegions()`），hit-test 不用单独改。
- README：跨行规则补「纯空行不画胶囊」+ 几何陷阱补 `location(forGlyphAt:)` 行底坑。

**验证**：`Emora` macOS 单 target（`/tmp/ev_mac_only.sh`，含 3 个既定 workaround）

## macOS 输入框：短文本行不该有满宽背景框（已修，09.19 反馈）

用户新截图：`解锁，屏幕顶端弹出一行字——`、`【气运签到系统已绑定。宿主：陆星河。】`
等短行文字只占一小截，但胶囊一路铺到行尾，空白区整片带底色。
要求：背景框只包住有文字的部分。

**根因**：同一个 `toneCapsuleGeometries()` 里 `boundingRect(forGlyphRange: sub, in:)`
会把**行尾换行 / 空白**一直算到容器右边界。独立 AppKit 探针
（`/tmp/ev_trim_probe.swift`，容器宽 1000）实测：无论长短，所有行 `br.width = 1000`，
而 `usedRect.width` 分别是 744.1 / 191.2 / 244.4 —— 之前满宽就是这么来的。

**修复**（`EmotionTokenTextView.swift` + README）：
- 新增 `capsuleTrimCharacters`（whitespacesAndNewlines + U+3000），⚠️ **不含 U+FFFC**：
  拟声 pill 是可见实体，行尾是它时胶囊必须继续包住（与判空集合
  `capsuleInvisibleCharacters` 的取舍正好相反，别合并成一个）。
- 回调里拿到 `chars` / `lineText` 判空后，用 `Unicode.Scalar(nsText.character(at:))`
  从首尾两端裁掉空白字符（UTF-16 surrogate → `Unicode.Scalar` 返回 nil，天然不会被误裁），
  再用 `glyphRange(forCharacterRange:)` 换回 glyph 范围取 `boundingRect`。
  `textRects` / `band` / `resolveCapsuleSeams` 全都跟着这份 br 走，接缝收敛不受影响。
- 探针结果：短行胶囊宽 `1000 → 207.2 / 260.4`（= 文字实宽 + 16pt 内边距），
  铺满的长行仍是 `760.1`；空行仍被上一条的判空逻辑跳过。
- README：表格补「宽度」一行 + 几何陷阱补「行尾空白必须裁掉」。

**验证**：`bash tools/ios_build.sh mac` 双 target → **✅ 全部构建通过**（21s），
日志无新增并发 / 类型警告。
⚠️ 待用户在真机目视确认：短行右端是否只剩 8pt 内边距、徽章是否仍贴左上角、
拟声 pill 所在行的胶囊有没有被裁过头。

## iOS 输入框：插入符（光标）比文字高出一倍（已修）

  重写 `caretRect(for:)`：`offset(from:to:)` 取字符下标 → `glyphRange(...length:0)` →
  `lineFragmentUsedRect(forGlyphAt:)` 拿到行片段高，减掉 `lineSpacing` 后
  用 `bodyFont.lineHeight` 兜底（段落末行没有行距，减完会小于字高）。
- ⚠️ **只改 `rect.size.height`，不动 origin**：super 给的 minY 就是行片段顶部、

  ⚠️ 必须保持 `false`（TextKit 1），子类里用的 `layoutManager` 在 TextKit 2 下无效。

## macOS 播放详情：4 个控制区固定、仅原文滚动（已修）
用户要求 `AudioPlayerDetailView` 的波形 / 走带 / 工具 / 属性四块常驻不滚动，
`PlayerTranscriptView` 正文自己滚。

**根因**：外层 `ScrollView` 把 5 块一起包进滚动内容；工作区此前又把
`PlayerTranscriptView` 内部 ScrollView 的 `.frame(maxHeight: 268)` 删了，
内层拿不到确定高度 → 退化为按内容撑高，文本实际跟着整页滚。
⚠️ 嵌套 ScrollView 想真正滚动，祖先链必须给出**有限且确定**的高度。

**修复（2 文件，零 pbxproj 改动）**：
- `AudioPlayerDetailView.swift`：外层 `ScrollView` → `VStack`；4 块与各自 padding 原样保留；
  `PlayerTranscriptView` 加 `.frame(maxWidth: .infinity, maxHeight: .infinity, alignment: .top)`
  后再 `.padding(.top, 18)`，作为 VStack 唯一 flexible 子视图独占剩余高度。
  ⚠️ frame 要放在 padding **前**（或显式 `alignment: .top`），否则卡片会在高 frame 里垂直居中。
- `PlayerTranscriptView.swift`：内部 ScrollView 补 `.frame(maxWidth: .infinity, maxHeight: .infinity)`，
  明确吃掉「卡片高度 − 标题行」。

**行为变化**：原文卡片现在占满右栏剩余高度（短文本时卡片内留白），超长才出滚动条。
若要卡片贴合内容高度，改成 `Spacer(minLength: 0)` + 卡片固定上限（原来的 268）。
