## 音色目录本地化改造（basic_voices.json v1 → v2）

### 背景
App 支持中英双语，但 `basic_voices.json` 里 `name`/`feature`/`scene`/`gender`/`lang` 全是中文原文，
`VoiceService.categoryPredicate` 也用中文硬匹配（`voiceScene == "日常对话"`），
导致本地化与筛选逻辑耦合；旗舰音色又硬编码在 `DatabaseManager.premiumVoices`，与 JSON 双份维护。

### 方案：语义 code + i18n 分组
JSON v2 结构（599 条：旗舰 2 + 基础 597）：
```json
{ "version": 2, "voices": [{
  "idx": 2, "key": "qwen-...-longrongzhihe",
  "tier": "premium|basic", "lang": "zh|en",
  "gender": "female|male|unknown", "age": 24,
  "scene": "daily|companion|...", "audio": "xxx.m4a",
  "zh": { "name": "蓉芷荷", "feature": "电台质感音" },
  "en": { "name": "Ada", "feature": "Radio" }
}]}
```
- 逻辑字段全部语义 code，筛选与语言彻底解耦
- 597 个音色各配一个**单单词**英文名（用户指定风格），全局唯一 599/599；
  8 个英文音色（lang=en）保留原名首词（"Olivia Lin" → "Olivia"），不占用中文名池
- 179 个 feature 全部翻译为英文短标签；旗舰的 `知心温暖`/`明亮开朗` 也纳入同一张表
- 脏数据修正：idx 403 的 `gender: "不能"` → `unknown`

### 关键文件改动
- 新增 `Models/VoiceCatalog.swift`：`VoiceTier`/`VoiceLangCode`/`VoiceGenderCode`/`VoiceSceneCode`
  + `AppLanguage.isChinese`（用 `Bundle.main.preferredLocalizations`）。**已加入 pbxproj**
- `Models/Voice.swift`：`Voice` 增 `nameEn`/`descEn`/`tier`/`lang` 等，提供
  `localizedName`/`localizedDesc`/`localizedAvatar`/`localizedScene`/`localizedGender`/`sortKey`；
  `category` 改为 computed（由 tier + lang 派生），`ageBucket` 改返回 `AgeBucket?`
- `Database/DatabaseManager.swift`：**删除硬编码 premiumVoices**，改为从 JSON 读 tier=premium；
  三条旧同步路径合并为 `syncVoicesIfNeeded()` + `resyncFromCatalog()`；
  新增 `migrateVoicesTable()` 用 `PRAGMA table_info` + ALTER TABLE 补列
  （tier/lang_code/gender_code/scene_key/name_en/desc_en）；fingerprintVersion 3 → 4
- `Services/VoiceService.swift`：谓词改比 code；搜索覆盖中英两列，
  场景/语种把「当前语言下名称命中」的 code 展开成 `IN (...)`（SQLite.swift: `array.contains(expr)`）；
  排序统一为「旗舰优先 + 当前语言展示名」，内存排序后切片
- `.localized()` 约定不变：中文原文当 key，新增 29 条文案到两个 Localizable.strings

### 新增工具（幂等，可重复执行）
- `tools/gen_basic_voices.py`：生成/重建 JSON v2，兼容读 v1 与 v2
- `tools/verify_voice_filtering.py`：Python+sqlite3 复刻 SQL 谓词，冒烟验证
  29 个分类命中数、分页一致性、场景/语言/年龄分类之和 == 总数、双语搜索、旗舰默认收藏

### 验证方式（本机 xcodebuild 包解析被沙箱挡住）
用 `swiftc -typecheck -disable-sandbox -swift-version 5` + DerivedData 里预编译的
SQLite/Supabase 模块做全量类型检查。需加 `-disable-sandbox`，否则 SwiftUI 宏插件服务报错。
基线对照：HEAD 与改动后报错完全一致（4 条，全在 `CreditsService.swift` 的
Swift6 actor 隔离问题，属既有问题）→ 本次零新增错误。
注：`Views/CreditsView/PackageCardView.swift` 是孤儿文件，未进 pbxproj，不参与编译。

## 第二轮：DatabaseManager 瘦身（用户要求，开发阶段不保留兼容）

### 删除 transactions 表
`transactions` 表是死代码——闭环只在 `Models/Transaction.swift` ↔ `CreditsService.swift`
（`fetchTransactions` / `addTransaction`）之间，无任何 UI 或业务调用方。
真正被 UI 消费的是 `consumption_records`（消耗记录）和 `purchase_records`（购买记录），保留。
已删：`Models/Transaction.swift` 文件、pbxproj 4 处引用、CreditsService 两个方法、
DatabaseManager 的 `transactions` 表与 `tx*` 表达式。

### 去掉全部旧版本兼容与迁移
用户明确：开发阶段不做迁移、不留历史数据。
- 删 `migrateVoicesTable()`（`PRAGMA table_info` + ALTER TABLE 那套）
- voices 表删掉全部历史兼容列：`category`、`scene`(中文)、`gender`(中文)、`lang`(中文)、`avatar`
  → 最终 12 列：`key / name / name_en / desc / desc_en / tier / is_favorite /
    scene_key / age / gender_code / audio / lang_code`
- 删 `BasicVoiceTemplate` 的 `avatar`/`avatarEn`，删 DatabaseManager 里的
  `categoryRawValue` / `genderRawValue` / `langRawValue` / `VoiceSceneCode.legacyChineseName` 扩展
- 删 `Voice.avatar`，`localizedAvatar` 改为从 `name` / `name_en` 直接算（不入库）
- 三条旧同步路径 → 简化为 `syncVoicesIfNeeded()` + `rebuildVoices(from:)`：
  清表前取收藏状态 → `voices.delete()` → 整批 insert → 旗舰默认收藏

### 新增：开发期表结构自动重置（关键，否则启动崩溃）
`create(ifNotExists:)` 不会改已有表，旧库缺 `name_en` 等列会让 init 走 `fatalError`。
加 `currentSchemaVersion`（UserDefaults）：
**改了 `createTables()` 里任何列，就把这个常量 +1**，启动时会 DROP 全部 4 张表重建，
同时清掉旧的 fingerprint 状态。
`Table.drop(ifExists:)` 来自 SQLite.swift 的 `Connection+Schema`（`db.run(table.drop(ifExists: true))`）。

### 踩坑
`try` 不能写在 `||` 短路表达式中间：`a || (try db.scalar(...))` 编译不过，
必须先单独 `let rowCount = try db.scalar(voices.count)`。

### 验证
- 类型检查：仍只剩 CreditsService 的 4 条基线 actor 隔离错误，零新增
- `tools/verify_voice_filtering.py` 同步精简表结构后重跑：ALL PASSED
- 列定义与实际使用逐项核对：12 列定义 vs 13 个使用项（含 `db.voices` 表），完全对齐

## 第四轮：VoicesLibraryView 翻页性能修复（CPU/内存飙升）

### 现象
快速连点「下一页」多次后，CPU 与内存都飙升。

### 根因
`reloadCurrentPage()` 在「纯翻页（查询签名不变）」时虽跳过了 totalCount/chipCounts 重算，
但**每次仍调用 `VoiceService.fetch/fetchFavorites`**，而二者每次都把「当前过滤条件下的全部命中音色」
全量读出、内存过滤、全量排序（`Self.sorted`），最后才切片出 16 条。
即每翻一页 = 全表读 + 全量排序一次，且**同步跑在主线程**。快速连点 → 多次主线程全量重查+排序，
大数组短时间内密集分配来不及释放 → CPU 飙、内存涨。

### 修复
- `VoiceService`：分页版 `fetch`/`fetchFavorites` + 私有 `slice` 删除，
  改为 `orderedVoices(showingFavorites:category:searchText:) -> [Voice]`，
  返回「过滤 + 排序」后的**完整有序数组**（不做切片）。
- `VoicesLibraryViewModel`：新增 `cachedOrderedVoices` 缓存。
  `reloadCurrentPage` 仅在查询签名（分类/搜索/收藏）变化时重查并填充缓存 + 用 `cachedOrderedVoices.count`
  作为 totalCount（省掉一次额外全表 count）；**纯翻页直接对缓存按 offset 切片**（`O(pageSize)`），
  不再全表重查 + 全量排序。
- `toggleFavorite`：收藏视图下取消收藏时从缓存移除该项并重算总数/页数；
  非收藏视图下只更新缓存项的 `isFavorite`（值类型可直接赋值），避免翻页般的重查。

### 效果
单次翻页成本从「全表读 + 全量排序」降到一次数组切片，连点翻页不再堆积主线程重活与临时大数组。
（动画叠加：`proxy.scrollTo` + 每卡 `delay(index*0.03)` 交错动画仍会随连点堆叠，属次要 CA 开销，本次未动。）

### 验证
静态核查：无对已删除方法的悬挂引用；类型自洽（`toggleFavorite` 返回 Bool、`Voice.isFavorite` 为可变 var）。
本机仍无法跑依赖解析版类型检查（xcodebuild 被沙箱挡）。

## 第五轮：翻页性能二次修复（用户反馈 CPU/内存仍暴涨）

### 复盘上一轮（第四轮）的问题
第四轮把 `cachedOrderedVoices` 设成**整份 `[Voice]` 全量数组常驻**——这反而让内存比改之前更高
（之前每页只临时建全量数组、用完即释放；改后 ~891 个 Voice 对象一直留着），
正是用户说的"之前的数据还被保留着"。数据层重排虽省了，但**翻页动画**仍在飙 CPU。

### 本轮修复
1. **缓存改为轻量有序 key 列表**：`cachedOrderedVoices: [Voice]` → `cachedOrderedKeys: [String]`。
   查询签名变化时只取 `orderedVoices(...).map(\.key)`（几十 KB），不再常驻全量 Voice 对象。
2. **翻页只取当前窗**：新增 `VoiceService.fetchByKeys(_:)`
   （`WHERE key IN (...)`，`Dictionary` 按传入顺序回填），只取 `pageSize` 个 Voice。
   上一页的 Voice 对象随 `displayedVoices` 被替换而释放 → 内存稳定，符合"之前的数据不保留"。
3. **砍掉动画堆叠（CPU 主因之一）**：
   - `VoiceCard` 的 `asymmetric` 入场（offset+scale+opacity + 单卡 `delay(index*0.03)` 交错，最长 ~0.83s）
     改为 `.transition(.asymmetric(insertion: .opacity, removal: .identity))` + 0.2s 淡入。
     removal 设 `.identity` 让旧卡片立即消失，快速连点不再层层堆叠淡出动画。
   - 删掉 `LazyVGrid` 上的 `.animation(value: voices.map(\.key))` 整组淡入兜底（重复触发、每次新建 String 数组）；
     ForEach 闭包参数 `index` 随之改为 `_`。

### 效果
- 内存：仅常驻「有序 key 列表」+ 当前一窗 Voice 对象，上一页数据随替换释放；不再常驻全量。
- CPU：翻页数据获取从「全表读+全量排序」降到「按 16 个 key 取窗」；动画从 ~0.83s 交错堆叠降到 0.2s 轻量淡入，连点不再叠加。

### 验证
`xcrun swiftc -parse` 三个改动文件（VoiceService / VoicesLibraryViewModel / VoicesLibraryView）零语法错误。
仍无法跑依赖解析版类型检查（沙箱挡 xcodebuild）。

## 第六轮：VoicesLibraryView 两个入口的首页/定位行为

### 需求
1. 左侧菜单进入 → 始终显示**第一页**（此前 `voiceLibraryCurrentPage` 持久化到 UserDefaults，
   重启后还会恢复上次页码）。
2. 从「更换」按钮的 `showVoiceLibrarySheet` 进入 → 显示**当前选中音色所在页**
   （`VoiceLibrarySheet` 弹 `VoicesLibraryView`，`appState.selectedVoice` 为当前在用音色）。

### 改动
- 新增入口枚举 `VoiceLibraryEntry { case menu; case sheet }`，`VoicesLibraryView.init(entry: .menu)`
  默认即左侧菜单；`VoiceLibrarySheet` 改传 `.sheet`。
- `VoicesLibraryView.onAppear` 按入口分流：
  - `.menu`：`vm.syncFromAppState(... currentPage: 1)` —— 恢复筛选状态但页码强制 1。
  - `.sheet`：`vm.jumpToVoice(appState.selectedVoice?.key)`。
- `VoicesLibraryViewModel` 新增：
  - `jumpToVoice(key:)`：重置筛选为「全部」（保证选中音色必在结果集内）、清空查询签名、重填
    `cachedOrderedKeys`、pending 待定位项，触发 `finalizePendingJump`（pageSize 未定则等待）。
  - `commitPageSize(_:)`：视图在几何测得**最终** pageSize 后调用（替代 `setPageSize`），
    置 `pageSizeFinalized = true` 后 `finalizePendingJump()`。
  - `finalizePendingJump()`：仅当 `pageSizeFinalized` 时在有序列表中定位 key、算 `index/pageSize+1`
    翻页，并置 `@Published scrollTargetVoiceKey = key`（供视图滚动）。
  - 字段：`pendingJumpToVoiceKey`、`pageSizeFinalized`、`scrollTargetVoiceKey`。
- 视图滚动用 `scrollTargetVoiceKey` 信号驱动（`.onChange(of: vm.scrollTargetVoiceKey)` →
  `proxy.scrollTo("voice-\(key)", anchor: .center)`），**摆脱 onAppear 与几何测量先后顺序的时序隐患**；
  删除原 `ScrollViewReader.onAppear` 里依赖旧页的滚动和 `didInitialScroll`。
- `onDisappear`：仅 `.menu` 入口才把筛选/页码写回 AppState；`.sheet` 不改写持久筛选状态
  （避免临时「更换音色」覆盖用户在库里的分类/收藏筛选）。

### 时序保障
`onAppear`（jumpToVoice）与几何 `commitPageSize` 谁先谁后都不影响最终定位：
`finalizePendingJump` 受 `pageSizeFinalized` 门控，且两者都会调用它；只有 pageSize 确定后才真正翻页，
翻页完成发信号滚动，故滚动一定作用在正确页面。

### 验证
`xcrun swiftc -parse` 全部改动文件（VM / View / VoiceLibrarySheet / AppState / VoiceService）零语法错误。
仍无法跑依赖解析版类型检查（沙箱挡 xcodebuild）。
