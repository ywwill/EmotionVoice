# 积分体系改造方案（问题 2 + 问题 3）

- 日期：2026-10-20
- 配套 SQL：`supabase/migrations/20261020_credits_hardening.sql`
- 配套函数骨架：`supabase/functions/verify-purchase/index.ts`
- 本轮只出方案，**未改动任何 Swift 源码**

---

## 0. 一句话结论

把余额从「客户端可写的一行数据」改成「**服务端原子记账 + 客户端乐观缓存**」：
云端是唯一真相源，客户端本地只保存「云端快照 + 待同步账本」，
所有余额变动带幂等键进流水账本，失败要可见、可重试、可对齐。

## 1. 现状与根因

### 1.1 当前数据流

```
                    ┌─────────────────────────────────────────┐
   macOS App        │        Supabase (PostgREST)             │
                    │                                         │
   deduct(points) ──┼──▶ UPDATE user_credits SET credits = X  │  ← anon 直接写
   addCredits(n)  ──┼──▶ UPSERT user_credits  (整行覆盖)      │  ← anon 直接写
   initializeUser ──┼──▶ UPSERT user_credits  (新用户送 50)   │  ← anon 直接写
                    │                                         │
   balance ◀────────┼─── UserDefaults "user_credits_balance"  │  本地才是权威
                    └─────────────────────────────────────────┘
```

调用点：`SupabaseManager.saveOrUpdateUser()` / `updateCredits()` / `addCredits()`
凭证：`Const.swift:13` 的 publishable key（**明文在 App 包里**）

### 1.2 问题 2 的根因

anon 角色对 `user_credits` 拥有 INSERT / UPDATE 权限，且 `device_id` 由客户端自称。
publishable key 就在包里 → **一行 curl 就能把任意 device_id 的余额改成任意值**：

```bash
curl -X PATCH "https://dpyyhbqqmegencxekkcr.supabase.co/rest/v1/user_credits?device_id=eq.<任意>" \
  -H "apikey: sb_publishable_hUevSD3cOSGgEMde6RHyUg_jaJRieeE" \
  -H "Content-Type: application/json" \
  -d '{"credits": 999999}'
```

即使加了 RLS「只能改自己的行」，也拦不住 —— 因为「自己」是客户端说了算。

### 1.3 问题 3 的根因

`CreditManager` 是**先改本地、再异步同步云端**，且两处失败都只打日志：

| 位置 | 行为 |
| --- | --- |
| `CreditManager.deduct()` :159 | 先改本地 UserDefaults，再 `syncToCloud()` |
| `syncToCloud()` :108 | 失败 → `Log(...)` 后结束 |
| `syncFromCloud()` :96 | 失败 → `Log(...)` 后继续用本地值 |

两个方向的后果：

| 场景 | 结果 |
| --- | --- |
| 内购到账 → 同步失败 → 重启 | `syncFromCloud` 用云端旧值覆盖本地 → **用户付了钱，积分蒸发** |
| 断网生成 → 重启 | 本地扣了、云端没扣 → 云端把余额补回来 → **无限白嫖** |

而且**重试本身也不安全**：现在的 `updateCredits()` 是「整行覆盖」，
网络超时后客户端不知道服务端到底有没有写入，重传一次就可能重复扣。

## 2. 目标架构

```
                    ┌──────────────────────────────────────────────────┐
   macOS App        │  Supabase                                        │
                    │                                                  │
  本地镜像 balance  │  ┌────────────────────────────────────────────┐  │
   = 云端快照       │  │ user_credits   anon: SELECT only           │  │
   - Σ(pending 扣费)│  │ credit_ledger  每笔变动留痕 + op_id 唯一   │  │
   + Σ(未入账内购)  │  └────────────────────────────────────────────┘  │
                    │        ▲                                          │
   pending 账本 ────┼────────┤ RPC（SECURITY DEFINER，服务端校验）      │
   (JSON 文件)      │  ensure_user / consume_credits                   │
                    │  grant_credits ← 仅 service_role                 │
                    │        ▲                                          │
   StoreKit 交易 ───┼──▶ Edge Function verify-purchase ────────────────┘
                    │    校验票据后调 grant_credits
```

职责划分：

| 角色 | 能做什么 |
| --- | --- |
| App（anon） | 读自己余额、调 `ensure_user`、调 `consume_credits` |
| App | **不能**直接写 `user_credits`，**不能**调 `grant_credits` |
| Edge Function（service_role） | 校验内购票据后调 `grant_credits` |
| 数据库 | 原子扣减、幂等去重、留痕、拒绝负余额 |

## 3. 问题 2 解法：收回写权限 + 原子 RPC

### 3.1 权限矩阵（前后对比）

| 对象 | 改前 | 改后 |
| --- | --- | --- |
| `user_credits` INSERT | anon 可 | ❌ 收回 |
| `user_credits` UPDATE | anon 可 | ❌ 收回 |
| `user_credits` SELECT | anon 可 | ✅ 只读自己那行 |
| `credit_ledger` | — | ❌ anon 全禁（含读） |
| `ensure_user()` | 不需要 | ✅ anon 可 |
| `consume_credits()` | 不需要 | ✅ anon 可（内部全额校验） |
| `grant_credits()` | 不需要 | ✅ **仅 service_role** |

### 3.2 三个 RPC（已在 SQL 中实现）

| RPC | 作用 | 关键保证 |
| --- | --- | --- |
| `ensure_user(device_id, region, device_info)` | 开户并补设备信息 | 新用户赠金走账本，`op_id='signup:<device_id>'` 保证只发一次 |
| `consume_credits(device_id, amount, op_id, meta)` | 扣费 | 单条 `UPDATE ... WHERE credits >= amount RETURNING` 靠行锁防并发超扣；`op_id` 唯一做幂等；余额不足抛 `INSUFFICIENT_CREDITS` 且不写账本 |
| `grant_credits(device_id, amount, op_id, kind, meta)` | 发放 | **不授予 anon**；内购用 `transactionId` 当 `op_id`，重传不重复发 |

返回统一为 `(balance numeric, applied boolean)`：
`applied=false` 表示命中幂等短路，这次没真正记账 —— 客户端据此判断「是重试」还是「新扣一笔」。

### 3.3 幂等键约定

| 场景 | op_id |
| --- | --- |
| 开户赠金 | `signup:<device_id>` |
| 一次音频生成扣费 | UUID，**在发起生成前就生成好**，重试全程复用同一个 |
| 内购入账 | `<StoreKit transactionId>` |

规则：**客户端生成、重试复用、服务端唯一约束兜底**。
这样即使客户端重试 10 次、或者两个进程并发重传，数据库也只记一笔。

调用语法按 supabase-swift 2.55.4：`rpc(_ fn: String, params: some Encodable) throws -> PostgrestFilterBuilder`

### 3.5 ⚠️ 防护边界（必须知道）

这套改动**能**防住：
- ✅ 随手 curl 改余额（写权限已收回，漏洞从「一行命令」变成「要逆向二进制」）
- ✅ 并发超扣（条件更新 + 行锁）
- ✅ 重复扣费 / 重复发积分（`op_id` 唯一约束）
- ✅ 余额变负数（服务端条件更新保证）

**防不住**：
- ❌ 专业攻击者逆向出 publishable key 后，仍然可以替**任意** `device_id` 调 `consume_credits`
  —— 也就是能**花光别人的余额**（DoS），虽然不能给自己加钱
- ❌ 任何客户端侧的 secret / HMAC 签名都同理：`APP_SECRET` 明文在包里，提取出来就能伪造

**根治路径（建议阶段 3）**：上 Supabase Auth 匿名登录

```
App 启动 → supabase.auth.signInAnonymously() → 拿到 JWT
         → ensure_user 时把 auth.uid() 写入 user_credits.auth_uid
         → RLS policy 改用 auth.uid() = auth_uid
         → 此时 device 与身份强绑定，伪造 header 无效
```

在此之前，缓解手段：单笔上限 10000（SQL 里已加）、按 device_id 做流速限制（可在 Edge Function 层加）。

## 4. 问题 3 解法：云端权威 + 本地待同步账本

### 4.1 状态模型

```
authoritativeBalance   云端真值（唯一权威，来自 RPC 返回值 / syncBalance）
pendingConsumes        [{opId, amount, meta}]   已本地预扣、未成功上报
pendingPurchases       [{transactionId, jws}]   已付款、未成功入账

显示余额 = authoritativeBalance − Σ(pendingConsumes) + Σ(未入账 purchase 积分)
syncState ∈ { .synced, .pending(count: Int), .failed(String) }
```

关键不变量：
1. **本地永不凭空加减**，只允许「云端真值 + 待同步增量」推导
2. **允许生成的前提**：`authoritativeBalance − Σ(pendingConsumes) ≥ 本次费用`
   （防止离线时无限预扣）
3. **pending 有上限**（建议 20 笔 / 累计 100 积分），超过则强制要求联网后再生成

### 4.2 ⚠️ pending 账本不要放 SQLite

项目现有的 DB 策略是「结构版本不符就 DROP 全部表重建」（`DatabaseManager` 的 fingerprint 机制）。
如果把待同步账本放进 SQLite，**某次 bump schema version 就会把用户还没上报的扣费记录清空** ——
又变成丢钱。

建议：**独立 JSON 文件 + 原子写**

```
~/Library/Application Support/<bundle id>/credits_pending.json
```

写入用 `data.write(to: url, options: .atomic)`，读失败就当空账本（宁可多扣也不能少扣？
不 —— 读失败时应该**禁止生成**，提示用户联网同步，因为无法确认已扣多少）。

> 附带好处：避开 P1-10 里 SQLite Connection 跨线程不安全的问题。

### 4.3 数据结构

```swift
struct PendingOperation: Codable, Identifiable {
    enum Kind: String, Codable { case consume, purchase }
    let id: String            // consume: opId(UUID) / purchase: transactionId
    let kind: Kind
    let amount: Double        // consume 为正数（表示要扣多少）
    let credits: Double?      // purchase: 对应积分数
    let jws: String?          // purchase: StoreKit jwsRepresentation
    let meta: [String: String]
    let createdAt: Date
    var attempts: Int = 0     // 重试次数，超过阈值转 .failed 提示用户
}
```

### 4.4 客户端改造点（逐文件）

**`Store/CreditManager.swift`**

```swift
// 新增
enum CreditSyncState: Equatable {
    case synced
    case pending(count: Int)
    case failed(String)
}
@Published private(set) var syncState: CreditSyncState = .synced

// deduct 改造后的语义（伪代码）
func consume(opId: String, amount: Double, meta: [String: String]) async -> Bool {
    // 1) 本地预扣校验（用含 pending 的可用余额）
    guard availableBalance >= amount else { return false }
    // 2) 先落盘 pending（崩溃也不会丢）
    pendingStore.append(.init(id: opId, kind: .consume, amount: amount, meta: meta))
    refreshDerivedBalance()
    // 3) 上报；失败留在 pending 里等下次
    await flushPending()
    return true
}

// flushPending：按序上报，成功即移除，全部完成后拉云端真值对齐
func flushPending() async {
    for op in pendingStore.all {
        do {
            let r = try await SupabaseManager.shared.consume(...)
            pendingStore.remove(op)
        } catch let e as RPC error where e is INSUFFICIENT_CREDITS {
            // 真没钱了：移除 pending（否则会一直卡住），并刷新真值
            pendingStore.remove(op); await syncBalance()
        } catch {
            op.attempts += 1
            syncState = .failed(...)
            break   // 网络问题：保留剩余 pending，等下次
        }
    }
    if pendingStore.isEmpty { await syncBalance() }
}
```

### 4.5 内购入账：为什么必须服务端参与

现在 `addCredits` 只改本地 → 同步失败就蒸发。
改成服务端入账后：交易落盘 + `transactionId` 幂等，**重传多少次都只发一次**，
而且即使 App 被删重装，只要 Keychain 里的 device_id 还在（或用户重新购买后凭票据恢复），账都能对上。

链路：

```
StoreKit 交易成功
   ↓  落盘 pendingPurchases（防丢）
   ↓  POST /functions/v1/verify-purchase  { deviceId, transactionId, jws, productId }
Edge Function
   ↓  验签 + 查 App Store Server API 确认交易有效、未退款、productId 匹配
   ↓  service_role 调 grant_credits(op_id = transactionId)
   ↓  返回新余额
App
   ↓  移除 pending，syncBalance 对齐显示
```

骨架已放在 `supabase/functions/verify-purchase/index.ts`，需要补的配置见该文件顶部注释。

### 4.6 UI 必须显示同步状态

不能再静默。建议在积分中心 / 设置页显示：

| syncState | 展示 |

## 5. 分阶段落地

| 阶段 | 内容 | 可独立上线 | 风险 |
| --- | --- | --- | --- |
| **0** | 在 Dashboard 跑 SQL 迁移；**先不动客户端** | ✅ | 无（老客户端会开始报错，见下） |
| **1** | 客户端切到 RPC：`ensure_user` + `consume_credits` | ✅ | 需与阶段 0 同批发布 |
| **2** | 引入 pending 账本 + syncState UI | ✅ | 中（改动 CreditManager 核心） |
| **3** | `verify-purchase` 服务端入账 + Supabase Auth 匿名登录 | ✅ | 高（涉及支付） |

⚠️ **阶段 0 与 1 必须同批**：SQL 收回写权限后，老客户端的 `saveOrUpdateUser` 会直接 401/403，
启动即报错。要么同批发版，要么阶段 0 先只建账本和 RPC、暂不 revoke（脚本里第 3 节单独注释掉即可），
等客户端全量更新后再补 revoke。

建议做法：**先跑第 1、2、4 节（建表 + RPC + 授权），跳过第 3 节 revoke**，
客户端发版并观察 1～2 天无异常后，再单独执行第 3 节收权限。

## 6. 回滚

| 阶段 | 回滚方式 |
| --- | --- |
| SQL | `grant insert, update on public.user_credits to anon;` 即可恢复老链路（账本保留无害） |
| 客户端 | 保留 `updateCredits()` 作为 fallback：RPC 返回 404（函数不存在）时退回旧路径，便于灰度 |

建议客户端加一个开关（UserDefaults 或远端配置），出问题时直接切回旧链路。
