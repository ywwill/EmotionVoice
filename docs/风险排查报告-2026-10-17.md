（`sk-964c3945bd89460f976f6b8bf13442b7` / `sk-557be4f42f724dd0848c08bc20f89c05`），
说明轮换过一轮但**没有换存储方式**，历史提交里仍留着旧 key。

3. 若短期做不到，至少放到不入库的 `xcconfig` + Info.plist 注入
4. `git filter-repo` 清理历史里的 key（清理后强推，通知所有协作者重新 clone）

### 2. 客户端可直写云端积分余额，无任何服务端校验

`SupabaseManager.updateCredits()`（`Supabase/SupabaseManager.swift:194`）用 publishable key
直接 `upsert` 到 `user_credits` 表，把 `credits` 字段写进去。

project ref 和 publishable key 在 `Const.swift` 里是明文 —— 拿到包就等于拿到了写权限，
一行 curl 就能把任意 device_id 的余额改成任意值。RLS 即使限制「只能改自己的行」也拦不住。

建议：客户端只读余额；增减必须走服务端（Supabase Edge Function 或自建后端）暴露的原子 RPC，
例如 `consume_credits(amount)`，在服务端做余额校验和扣减。

### 3. 本地余额是唯一权威，同步失败静默吞掉 → 双向资金漏洞

`Store/CreditManager.swift`：
- `deduct()`（:159）先改本地 UserDefaults，再 `syncToCloud()`；失败只打日志（:108）
- `syncFromCloud()`（:80）失败也只打日志，继续用本地值（:96）

两个方向的后果：

| 场景 | 结果 |
| --- | --- |
| 内购到账后同步失败 → 重启 | `syncFromCloud` 用云端旧值覆盖本地，**用户已付款的积分蒸发** |
| 断网生成 → 重启 | 本地扣了、云端没扣，云端把余额补回来，**可以无限白嫖** |

另外本地余额就是 `UserDefaults` 的 `user_credits_balance`（:48），
终端一行 `defaults write` 就能改。

建议：以云端为唯一真相源，本地只做离线缓存；离线扣费要落「待同步账本」并在联网时补传；
同步失败要给用户可见提示 + 重试，而不是静默吞掉。

### 4. 沙盒已开启但没有 entitlements 文件

`EmotionVoice.xcodeproj`：`ENABLE_APP_SANDBOX = YES`，但工程里**没有任何 `*.entitlements`**，
`CODE_SIGN_ENTITLEMENTS` 为空。

推断缺失（需 Release 包实测确认）：
- `com.apple.security.network.client` → 出站网络（WebSocket TTS + Supabase）可能被拒，
  正式包里所有联网功能失效
- `com.apple.security.files.user-selected.read-write` → `AppState.exportDirectory`
  拿不到持久访问权限，导出音频会失败

另外 `DatabaseManager`（:97）和 `AudioItem.swift`（:16）都把数据写进 `Documents/`，
沙盒下会被重定向到 `~/Library/Containers/<bundleid>/Data/Documents`，
用户在 Finder 里找不到自己的音频。建议改到 `Application Support/<bundle id>/`。

## P1 · 高（功能 / 稳定性）

### 5. TTS 链路可能永久挂起，并堵死所有后续请求

`Services/BailianTTSService.swift`：
- `waitForTaskStarted()`（:654）`while !receivedTaskStarted` **无超时**；
  `receive()` 出错就调 `reconnectAndReceive()`（:628），但重连后**不会重发 run-task**，
  新连接上永远等不到 `task-started` → 死循环
- `AsyncMutex`（:130）把所有 TTS 串行化 → 一次挂起 = 之后所有生成请求永久排队，
  `isGenerating` 永远转圈，只能杀进程
- `performSynthesize` 收流的 `while`（:237）同样无超时

建议：整段任务包一层 `withTimeout`；重连后必须整段重跑，而不是在原地继续 receive。

### 6. 取消生成是假的

`VoiceStudioViewModel.generate()`（:367）里的 `Task {}` **没有保存句柄**；
`cancelGeneration()`（:533）只置 `isGenerating = false` 并关连接，**不 cancel Task**。

后果：Task 继续跑 → `withCheckedThrowingContinuation` 永不 resume（协程泄漏）；
运气好跑完了还会**继续写文件、入库、扣费** —— 用户点了取消却被扣了钱。

建议：持有 `Task` 句柄，取消时 `task.cancel()`；给 continuation 加超时兜底。

### 7. 积分算多了：预估用的是带装饰字的 `text`

`VoiceStudioViewModel.estimatedPoints`（:225）→ `TextSplitter.calculateCharCount(text)`。
但 `text` 是把 token 的中文 label 拼进去的结果（"…笑声…愤怒…"），
代码注释（:217）自己写明「那些字是编辑器里的 UI 装饰，不是用户输入的台词」。
真正发给 API 的是 `ttsItems.toTTSSegments()`。

→ 每插一个标签多算 2~4 个字符的钱，用户被多扣。

建议：预估和实扣统一改用 `plainText` / segments 的真实字符数。

### 8. 主线程同步磁盘 I/O

`generate()` 是 `@MainActor`，内部 `Task {}` 继承 MainActor，因此：
- `audioData.write(to: tempAudioURL)`（:425）—— 几十 MB 写盘
- `AudioDuration.read()` 里的 `Data(contentsOf: .mappedIfSafe)`（`Extension/AudioDuration.swift:93`）

都在主线程执行，长音频生成完成时会明显卡顿。建议挪到 `Task.detached` / 后台 actor。

### 9. 每个音频块新建一个 Task

`VoiceStudioViewModel:386`，`onAudio` 回调里 `Task { @MainActor in … }`。
WebSocket 一秒几十上百块 = 上百个 Task。注释说做了节流，但节流只在
`GenerationStats.receive()` 内部，**Task 创建本身没节流**。

### 10. SQLite Connection 跨线程共用

`DatabaseManager.shared.db` 是单个 `Connection`；`CreditsService` / `ProjectService` /
`VoiceService` 都不是 `@MainActor`，可从任意线程调用。SQLite.swift 的 `Connection` 非线程安全
→ 并发读写有崩溃 / 数据损坏风险（`SQLITE_BUSY` / `SQLITE_MISUSE`）。

建议：统一到一个串行队列或 actor，或至少启用 busy timeout 并全部走主线程。

### 11. 数据库初始化直接 `fatalError` + 改表结构不生效

- `DatabaseManager.swift:107` 建库失败（磁盘满 / 权限异常）直接崩溃，无提示
- `createTables()` 全用 `ifNotExists: true`，**没有任何 `ALTER TABLE` 或版本化迁移**；
  代码里找不到 `resetDatabaseIfSchemaChanged` / `currentSchemaVersion`（记忆里记的
  「结构不符就 DROP 重建」策略在当前代码中不存在）
  → 加了新列后，老用户升级会读到不存在的列而崩溃
- `FileManager...first!` 强解包（:98、`AudioItem.swift:17`）
